## 摘要
扩散语言模型通过多次前向传播来精化一个固定大小的 token 位置块以生成文本，这一循环与大多数 LLM 服务系统所采用的每次前向执行单元并不匹配。稠密 MoE 运行时将所有工作绑定到精化迭代时钟：它在每次前向时重建相似的路由结构，为 logits 已经失效的位置重新计算专家输出，并将这些位置送入稠密的专家并行集合通信。本文提出 \sys{}，一种将扩散块视为编译单元的服务系统。\sys{} 为一个扩散块的块时钟结构编译一个小型 \emph{块计划}，并在迭代时钟上刷新所有可能影响活跃解码决策的值。\sys{} 沿 MoE 前向的三个稠密轴实现该计划：\atlas{} 为每层编译覆盖率驱动的活跃专家支持集，同时在每次迭代重算门控 logits；\lsp{} 将完整序列分片保留为模型状态，但仅将活跃、新解码以及需要刷新的位置路由到新的路由专家计算中；\freshlane{} 将这一新的 token--专家工作列表经过专家并行分发、内核和合并，然后在层边界恢复稠密逻辑分片。我们在 8 块 NVIDIA H100 GPU 上实现 \sys{}，并在三个开放权重的块扩散 MoE 模型（LLaDA-MoE、LLaDA2.0-mini 和 LLaDA2.0-Flash，总参数量从 7B 到 100B）上，跨 GSM8K、HumanEval、MGSM 和 MT-Bench 进行评估。在相同的 8-GPU 部署下，\sys{} 相比最强的仍可运行基线将端到端执行时间最多提升 2.7$\times$，并且在多个基线因内存耗尽而无法运行的最大批量大小下仍然可行，同时相对于稠密参考保持任务质量。

## Abstract
Diffusion language models generate text by refining a fixed-size block of token positions through many forward passes, a loop that does not match the per-forward execution unit used by most LLM serving systems. A dense MoE runtime binds all work to the refinement-iteration clock: it rebuilds similar routing structure on every forward, recomputes expert outputs for positions whose logits are already dead, and sends those positions through dense expert-parallel collectives. This paper presents \sys{}, a serving system that treats the diffusion block as a compilation unit. \sys{} compiles a small \emph{block plan} for the block-clock structure of one diffusion block and refreshes every value that can affect a live decode decision on the iteration clock.   \sys{} realizes this plan along three dense axes of an MoE forward: \atlas{} compiles a coverage-driven active expert support per layer while recomputing gate logits every iteration; \lsp{} keeps full sequence shards as model state but routes only live, newly decoded, and refresh-required positions through fresh routed-expert computation; \freshlane{} carries this fresh token--expert worklist through expert-parallel dispatch, kernels, and combine, then restores the dense logical shard at the layer boundary. We implement \sys{} on 8 NVIDIA H100 GPUs and evaluate it on three open-weight block-diffusion MoE models (LLaDA-MoE, LLaDA2.0-mini, and LLaDA2.0-Flash, spanning 7B to 100B total parameters) across GSM8K, HumanEval, MGSM, and MT-Bench. \sys{} improves end-to-end execution time by up to 2.7$\times$ over the strongest surviving baseline under the same 8-GPU placement and remains feasible at the largest batch sizes where multiple baselines run out of memory, while preserving task quality relative to the dense reference.

## 1. 核心问题与整体含义

- **背景**：主流 LLM 服务系统（vLLM、SGLang、Orca 等）默认"每次前向生成一个 token"，调度、批处理、并行与显存管理都围绕单次前向构建，适配自回归（AR）解码。
- **不匹配**：扩散语言模型（dLLM）采用完全不同的循环——初始化一个固定大小的 Mask token 块，反复跑完整 Transformer 前向，提交高置信位置，直到块内全部解码。**同一批位置在最终确定前会被完整模型处理多次**。
- **代价**：MoE 是 dLLM 前向的主要成本（优化后基线中占 60%（BS=1）至 77%（BS=32）），而稠密 MoE 运行时把所有工作绑定到"迭代时钟"：
  - 每轮重建相似的路由结构；
  - 为 logits 已经"死亡"（已提交）的位置重算专家输出；
  - 把这些位置继续送入稠密的专家并行 dispatch/combine 与 LM head。
- **核心洞察（两个时钟）**：
  - *迭代时钟*：每次精炼前向推进，改变隐藏状态、路由 logits、专家输出与解码决策——**不可重放**；
  - *块时钟*：仅在新块开始时推进，活跃专家支持集、序列分片归属、缓存描述符、紧凑载荷布局可**一次规划、多次摊销**。
- **契约**：缓存稳定的块结构，重算所有喂给活跃解码决策的值。论文主张扩散块应成为比"一次前向"更大、比"一个请求"更小的**编译单元**。

## 2. 方法论

### 2.1 总体设计
- **块计划（Block Plan）**：块开始时由调度器编译，仅存标识符与版本——每层活跃专家支持集 {S_l}、序列分片归属、解码缓存描述符、紧凑载荷布局、cold/hot-update/hot-skip 三类路径计数器；**不存**隐藏状态、路由 logits、专家权重或输出 logits。
- **生命周期**：cold 阶段初始化 → 多次 hot 阶段（划分 live / 新解码 / 稳定解码 / 需刷新）→ refresh 阶段（全量走新鲜路径重置缓存年龄）→ 块退出即销毁所有块局部状态；**任何缓存对象不跨块边界**。
- **失败封闭（fail-closed）**：版本不匹配、缓存缺失、形状不符、活跃性转移异常，一律回退到全新鲜（稠密）路径。

### 2.2 Expert Atlas（专家轴）
- 编译"活跃专家支持集"而**不是**路由结果：hot 迭代仍用当前隐藏状态重算 gate logits 与 top-k 权重，只是最终选择被限制在 S_l 内；绝不重放上一轮的 topk_ids / topk_weights。
- **Algorithm 1（有界覆盖规划器）**：
  1. 候选扩展：取 top-(K+m) 并归一化权重；
  2. 每 token 设定目标覆盖质量 r_t = α·Σ_{j=1..K} W_{t,j}，按专家累计质量 p_e 选初始 B 个专家；
  3. 迭代修复：计算每 token 已覆盖质量 C_t，找欠覆盖集合 U；对支持集外专家打分 score_e = H_e + βG_e（H_e 为"可满足剩余 token 数"，G_e 为"可补足的未覆盖质量"），每轮加入 top-c 正分专家，直至 |U|/N ≤ 1−q 或达到轮次上限 R；
  4. 若必须扩到全集，该层退化为稠密路由。
- **覆盖与放置分离**：支持集决定"哪些全局专家可用"，专家并行放置映射不变；S_l 被转成对现有映射的 dispatch 掩码。

### 2.3 Liveness-Shard Parallelism（token 状态轴）
- 关键区分：**已解码位置的 logits 是死的，但隐藏状态仍是模型状态**（双向注意力下仍影响后续层与后续迭代），因此不能删除。
- 两套掩码：D_i（当前已解码）∩ D_{i−1}（上一前向已解码）= 稳定解码 Z_i，**只有 Z_i 可复用缓存**；D_i \ D_{i−1} = 新解码 N_i，必须在其"已提交身份"下做一次新鲜计算后才可入缓存。
- **Algorithm 2（hot 迭代骨架）**：
  1. 由 token id 得到 live mask 与 decoded mask；
  2. 求 Z、N，判断是否到刷新周期 M_C；
  3. 逐 MoE 层：刷新或缓存缺失 → 全新鲜；否则新鲜集 F = ¬Z；
  4. Compact 出新鲜 token 稠密工作列表 → 用当前隐藏状态重算 gate logits → 在 S_l 内路由 → 稀疏 MoE → 生成完整分片目标缓冲（稳定解码读缓存）→ 把新鲜输出 scatter 回逻辑位置 → 更新缓存（含新解码位置）→ 层收尾；
  5. 本地解码 live 位置并保存 decoded mask 供下一前向使用。
- 输出路径同样按分片归属只对 live 位置物化 logits，返回紧凑提交决策。

### 2.4 FreshLane Dispatch（载荷轴）
- 把新鲜 token–专家工作列表变成专家并行 dispatch/combine 的**真实载荷**，紧凑表示只存在于 MoE 通信区间内，层边界恢复完整逻辑分片。
- 三步通信契约：
  1. **Packing & Dispatch**：各 rank 先交换新鲜行计数，紧凑打包；静态形状后端可 padding 并标记无效（shadow rows，由逻辑守卫保护）；
  2. **Light-traffic expert kernel**：同一融合 MoE 内核作用于更小工作列表，无效槽位在形成专家块前剔除或不参与归约；
  3. **Sparse update / Combine / Cache merge**：按偏移反向 combine，scatter 回完整分片，稳定解码位置由缓存填充。
- 避免两种失败模式：稠密通信外壳（跳过内核但通信仍按全 token 尺寸）与稀疏张量泄漏（注意力/残差/归一化需要完整序列）。

### 2.5 正确性边界
- **精确包络**：若 S_l 覆盖稠密路由器对每个新鲜 token 的选择，且解码缓存被禁用或每次使用前刷新，则 Epoch 与稠密执行器评估相同的有效 token–专家对，差异仅来自浮点归约/集合通信的非结合性。
- **路由支持界**：规划器目标 C_{l,t}(S_l) ≥ αR_{l,t}，成功时 |U_l| ≤ (1−q)N；未达标则扩大支持集、hot 路径刷新或退化为稠密支持。这是**路由质量界，不是文本语义相同的证明**。
- **解码缓存年龄界**：稳定解码缓存条目最多复用 M_C − 1 次 hot 迭代（0 ≤ age ≤ M_C − 1），键含块、层、rank 局部位置与版本。
- **决策稳定性条件**：设 Γ 为 top-1/top-2 间隔与阈值解码器余量的较小者，若 ∥ẑ − z∥∞ < Γ，则 Epoch 与稠密执行器选同一 top token、做相同提交决策。
- **运行不变式**：每轮必算 live 位置路由 logits、live token top-k 权重与专家输出、live 位置 logits、解码决策；只允许缓存支持集成员、token 归属、紧凑索引、集合通信尺寸与稳定解码的有界龄输出。

## 3. 实验设计

- **数据集 / 场景**：GSM8K（小学数学）、HumanEval（代码合成）、MGSM（多语言推理）、MT-Bench（开放式对话）。
- **模型**：三个开放权重块扩散 MoE 模型，参数跨度一个数量级：
  - LLaDA-MoE（1B 激活 / 7B 总参数）
  - LLaDA2.0-mini（1.4B 激活 / 16B 总参数）
  - LLaDA2.0-Flash（6.1B 激活 / 100B 总参数）
  - 统一 4096 上下文、默认块大小 32、贪心阈值解码 τ = 0.95、每块最多 64 步精炼、全解码后提前退出。
- **对比基线**：
  - 外部：dInfer（无缓存）、dInfer（启用逐位置缓存，最强公开缓存基线）、SGLang（近期块扩散支持，代表 AR 式运行时）；
  - 内部消融：full compute（无任何松弛）、w/o Expert Atlas（仅 token 侧稀疏）、w/o Liveness-Shard Parallelism（仅专家侧稀疏）。
- **部署**：所有系统固定并行放置 DP=1、TP=8、EP=8、SP=8（EP 定义专家归属与 dispatch/combine 组，TP 定义稠密张量并行与序列分片组，故 SP = TP）。
- **指标**：端到端请求执行时间、每迭代延迟、每前向组件时间、硬件计数器的计算/访存/通信相对开销、在线服务 P95 ITL vs QPS；质量用任务准确率与 MT-Bench 分数。
